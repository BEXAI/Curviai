## P21-01: seller-visible pack resolution cases

**Evidence and rationale.** [`support.ts`](../../apps/web/src/lib/support.ts) validates and delivers a message with server-checked job context. [`feedback/db-store.ts`](../../apps/web/src/lib/feedback/db-store.ts) records one answer per job/person and notifies the founder. Neither exposes a seller-visible case lifecycle. [`ops/grants.ts`](../../apps/web/src/lib/ops/grants.ts) already supplies audited, idempotent credit corrections. A case should connect these pieces so a seller can distinguish a received report from a resolved problem.

**Proposed changes.** Add a case link from the pack/support flow with issue category, optional shot/version reference and a concise description. Show the reporting seller a timeline with received, reviewing, awaiting seller and resolved states, plus the explanation and next action. Add an operator queue and separate private notes. Reference the existing feedback/support submission rather than sending duplicate intake messages. Permit at most one open case for the same workspace, job and category; reopening follows an explicit policy. A resolution may explain a limitation, request a new source photo, or link to an existing authorized action. It does not automatically grant credits, refund money, regenerate an image or expose withheld assets.

**Dependencies and decisions.** P18-05 feedback and P20-24/25 support; P20-46/49/66 operator actions, MFA and audit. Agree who may see a case in a team, reopening rules, retention and compensation policy before implementation. Proposed initial visibility is the reporting member plus workspace owner/admin; client/editor roles cannot read other members' private messages by default. Existing email support remains available.

**Security and data.** Proposed tenant tables hold `workspace_id`, immutable job/shot/version references, public case events and separately protected operator notes. Enforce parent/tenant consistency and RLS with cross-workspace tests; operator notes are never returned by customer serializers. Escape free text, cap/rate-limit submissions and omit message bodies from analytics. Preserve current source-media expiry; a case does not copy or extend photo retention. Deletion/export behavior must be specified alongside the migration. Any compensation uses the existing operator authorization and idempotency key, linked to the case audit.

**Acceptance.** A seller submits once, reloads and sees the same case and status; a duplicate submission creates no extra case or notification. Another tenant and an unauthorized teammate cannot access it. Private notes never reach customer HTML/API responses. Two concurrent resolutions cannot issue the same compensation twice. A source that has expired produces an honest request for a new photo. Keyboard and screen-reader checks cover submission, validation and timeline updates.

**External setup.** No new vendor. Use the configured transactional sender only after its existing staging delivery gate passes. Founder approves triage ownership and customer-facing policy before a pilot; this proposal adds no reply-time or refund promise.

## P21-02: workspace credit planning and optional owner budget

**Evidence and rationale.** [`billing/history.ts`](../../apps/web/src/lib/billing/history.ts) groups ledger movements per pack and labels active holds. [`api-v1/actions.ts`](../../apps/web/src/lib/api-v1/actions.ts) already routes API/MCP creation through the same service and estimate/hold checks as the app. [`spend-policy.ts`](../../trigger/src/spend-policy.ts) and [`caps.ts`](../../packages/ai/src/caps.ts) protect provider-dollar economics. There is no customer consumption projection or owner-configured credit budget in these paths. Sellers need credits planning; operator cost ceilings answer a different question.

**Proposed changes.** First add a read-only workspace view of available credits, active holds, delivered consumption, returned credits and a clearly labeled consumption projection. Link every figure to the existing ledger/history. Use a documented observation window and display insufficient history instead of a precise forecast when data is sparse. Then, only if accepted, add an owner-set credit ceiling for an explicitly displayed period, disabled by default. Show remaining headroom in pack estimates and give the same actionable refusal across app, API and MCP. Do not buy credits, change a subscription, alter credit expiry or schedule generation.

**Dependencies and decisions.** P20 ledger/reconciliation and billing-history acceptance must pass first. Settle budget-period/reset policy, treatment of corrections and who may view/change limits; proposed first scope lets only the owner change them. Keep limits/calculation policy in seeded configuration and workspace preferences. A read-only pilot can ship independently; budget enforcement requires a separate acceptance decision and migration review.

**Security and data.** Read raw ledger reasons and holds rather than treating grouped history's net delta as consumption. Define one authoritative accounting rule so reservation, delivered charge and release never count the same work twice. Enforce optional limits inside the existing workspace reservation lock, covering new jobs and every follow-up, including API/MCP entrypoints. Existing balance, entitlement and provider-dollar limits still apply. A budget change or period rollover cannot revoke already reserved work; outstanding holds must remain accounted for until settlement. Scope aggregates by workspace, apply RLS to preferences and audit owner changes. Store no new payment details and expose no provider margin data.

**Acceptance.** Fixtures reconcile the view to charges, pending holds, releases, grants and corrections, including failed/canceled jobs and partial delivery. Sparse or irregular history has explicit caveats. Concurrent starts that together exceed the optional ceiling admit only the affordable work. Replays, retries, regeneration, rollover and cancellation cannot bypass the ceiling or return headroom twice. A lowered limit blocks new reservations without stranding existing ones. Editor/client, raw PostgREST and OAuth attempts cannot raise or disable an owner budget. The read-only feature leaves billing/ledger writes unchanged; budget-disabled behavior matches current behavior.

**External setup.** None for the initial in-app view. Any later emailed threshold alert requires explicit preference, shared suppression/deduplication and existing sender proof. No new analytics vendor or financial forecast guarantee is proposed.

## P21-03: private outbound pack completion webhooks

**Evidence and rationale.** [P19](PHASE_19.md) explicitly leaves `pack.completed` MCP Events as backlog because subscription storage and webhook delivery are missing; current clients poll `get_pack`. [`api-v1/actions.ts`](../../apps/web/src/lib/api-v1/actions.ts) already provides authenticated pack fetch. [`trigger/src/db-store.ts`](../../trigger/src/db-store.ts) and [`jobs/settle.ts`](../../apps/web/src/lib/jobs/settle.ts) contain normal and interrupted terminal transitions. The schema has no outbound subscription/delivery tables. This candidate promotes that backlog's private API delivery foundation; native MCP Events protocol exposure remains deferred.

**Proposed changes.** Pilot one opt-in, versioned terminal-event contract for a workspace's pack runs. Include stable event ID, job/run identity, outcome, timestamp and an authenticated fetch location. Add owner/admin endpoint management, destination verification, delivery status, disable and controlled replay. Write an outbox entry atomically with every eligible terminal transition, including reconciliation/cancellation. Define follow-up runs explicitly so a regenerated pack creates a new run event while replaying the same run keeps its event ID. Deliver with bounded retries/backoff, endpoint quotas and an expiry policy. Document at-least-once delivery and possible reordering; receivers deduplicate by event ID and fetch current pack state.

**Dependencies and decisions.** P19 authenticated API contract and P20 terminal-state/recovery proof. A real integration owner must provide a consenting test endpoint and choose required latency before acceptance. Assess whether a bounded delivery batch fits the existing leased [`cron-tick.ts`](../../apps/web/src/lib/cron-tick.ts); do not imply instant delivery on its cadence. If it cannot fit without delaying critical jobs, propose worker capacity and cost separately before provisioning. Scope excludes marketplace publishing, OAuth grant changes, workflow builders and MCP Events activation.

**Security and data.** Tenant-owned subscriptions/outbox require RLS and consistent parent ownership; signing material is server-only, encrypted and rotatable. Sign the exact request bytes with timestamp and key ID; document receiver replay-window verification. Verify endpoint ownership and HTTPS destination safety on setup and every attempt, including DNS rebinding, private/link-local/metadata IPs, ports and redirects. Pin the vetted address during connection; redirects are refused. Never send source photos, prompts, tokens or presigned download URLs. Bound request/response size, connect/total timeout, attempts and concurrent deliveries. Do not persist response bodies or sensitive URL credentials. Disable/delete/revoke operations prevent future attempts; workspace deletion cancels deliveries and applies the agreed minimal metadata retention.

**Acceptance.** A crash after terminal commit cannot lose an event; a crash after receiver success may repeat delivery with the same ID. Normal completion, failure, cancellation, reconciliation and later follow-ups have contract tests. Concurrent delivery workers cannot claim the same attempt. Signature tampering, stale timestamps and rotated keys have receiver-fixture coverage. Cross-tenant access, blocked IPs, DNS rebinding, redirect chains, slow endpoints and oversized replies fail safely. Retry exhaustion is visible without blocking pack generation or existing cron work. An opted-in endpoint receives a staging event and can retrieve its pack using its own authorized API credential.

**External setup.** A customer-controlled HTTPS receiver and an explicit activation step. Recheck the chosen signing/transport libraries against their official documentation at implementation and record the date in `docs/verification.md`; no provider contract or hosting purchase is assumed here.
