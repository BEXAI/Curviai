# Inert runtime for a migration handoff

`node ops/maintenance-server.mjs` is a temporary replacement for the existing Render start command. It starts a native Node HTTP server from the repository root. It does not load Next.js, instrumentation, workers, database clients, provider integrations or the app's environment helper. It has no outbound network operations, body parser, filesystem access, job processing or database writes. It reads only `PORT` and the public `RENDER_GIT_COMMIT` identifier through its own small validated configuration helper. Stored service secrets remain untouched.

Only exact `GET /api/health` returns HTTP 200. Its JSON is `{ "mode": "migration_maintenance", "applicationReady": false, "commit": "<full SHA>" }`. This is readiness of the inert process only. Authorization headers do not enable protected details; they receive the same inert response. It deliberately omits the application's `ok` and `status` fields, and does not satisfy the ordinary application or protected release health contract. A missing commit is represented as `null` for local use; a live handoff requires the full expected deployment SHA. Invalid supplied commits or ports fail startup without logging their values.

All other valid HTTP requests receive 503 and `Retry-After: 60`, including HEAD, query-suffixed health URLs, cron, webhook, operator, MCP, upgrade and CONNECT requests. Responses use `Cache-Control: no-store` and close the connection. Malformed HTTP may be rejected by Node's HTTP parser. SIGINT and SIGTERM stop accepting connections; an existing connection cannot receive a new healthy response after shutdown begins. Remaining sockets close within five seconds.

## Operator sequence

1. Record the current Render start command, health check path, deployment SHA and deployment controls. Verify the candidate artifact contains this runtime and the compatible app. Review build and pre-deploy commands separately: an inert start command does not make a build hook safe. At the 2026-10-03 live read, the start command was `pnpm --filter @curvi/web start` and the health check path was empty. The source Blueprint differed; re-read the actual service and preserve those exact values for restoration.
2. Pause scheduled and external writers, prevent unrelated deployments, and deploy the exact checked candidate with `node ops/maintenance-server.mjs` as the temporary start command and an explicit `/api/health` health check. Read back the saved settings, exact live deployment and maintenance response SHA. An empty health check path does not establish HTTP health validation.
3. Prove every previous app instance has stopped, in-flight jobs and cron runs have finished, and other database writers are fenced before SQL. A 200 maintenance response, a routed 503 page or zero job counts alone cannot establish that fence. This runtime neither stops another process nor revokes a database session. Do not begin SQL if any writer or instance retirement remains uncertain.
4. Execute the separately reviewed transaction only after its journal, schema, writer-isolation, compatibility and recovery guards pass. Verify the committed migration hashes and postflight database invariants while the web process remains inert. Do not substitute the maintenance endpoint for a schema check.
5. Restore the exact recorded app start command, retaining the explicit `/api/health` check while deploying the same checked compatible artifact. Verify the ordinary application's exact SHA and current schema through its existing health contract before restoring the original health check setting. Check affected customer flows and job ownership before resuming writers and normal deployment controls.

Before any SQL commits, an aborted handoff can restore the prior verified app command and artifact after confirming the schema is unchanged. After SQL commits, keep the service inert if validation or app startup fails and follow the reviewed forward recovery procedure. Do not deploy an older incompatible writer or downgrade the schema as an automatic rollback. Local disk and GitHub preserve source code; they do not restore database data. There is no encrypted-backup provisioning or prerequisite in this handoff.

## Local verification

Run `node --test ops/maintenance-server.test.mjs` with Node 22. Tests require no package installation, credentials, database or providers. They cover configuration validation, allowed health identity, route and method rejection, upload expectations, protocol upgrades, termination and the bounded socket drain. Normal application health and release guards are unchanged.

Render documents [public maintenance isolation](https://render.com/docs/maintenance-mode), [per-instance HTTP health checks](https://render.com/docs/health-checks), and [overlapping deployment and old-instance shutdown](https://render.com/docs/deploys). Recheck actual service state during execution; the existence of these controls does not prove they have taken effect.
