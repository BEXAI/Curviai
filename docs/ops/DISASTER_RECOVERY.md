Record actual resource identifiers and verified settings in `docs/verification.md`; no successful database restore or recovery-time guarantee is established. Secret values belong in the password manager and service dashboards, never this document, logs or test reports.

## Incident containment and recovery assessment

1. **Contain and select.** Preserve the affected database/service and incident evidence. Stop affected writes with the approved maintenance and worker controls when necessary; a public maintenance page alone does not fence every writer. Record the last verified app SHA, migration journal and observed data effects.
2. **Recover code and configuration.** Use local files or GitHub to recover the reviewed source commit and its migration files. Reconcile the settings inventory below with the existing service dashboards. Neither source history nor rebuilding an empty schema recovers live customer rows, Auth identities, ledger state or R2 objects.
3. **Assess the actual data incident.** Determine which rows/objects remain and whether a reversible transaction, reviewed forward repair or compatible app rollback addresses the defect. Do not assume an encrypted artifact, decryption key or restore service exists. Existing recovery artifacts, if any, remain untouched. The [retired procedure](archive/BACKUP_RESTORE_PRE_2026-10-03.md) is historical reference, not an active setup or release requirement.
4. **Review before changing data.** Identify the exact target, old and new writer compatibility, isolation controls and rollback limits. Report any proposed irreversible deletion or replacement and the known data-loss consequence before proceeding. Never place a live database dump, Auth data or secrets in GitHub.
5. **Validate before any app connection.** If an incident-specific repair or replacement is authorized, verify migration history, row-level security, table grants, ledger function grants, tenant isolation, balances and job ownership before reconnecting. Any separately authorized data import must preserve these controls and must not restart old provider work or resend billing/email events. Code rollback alone does not roll back data.
6. **Reconnect in order.** Reconnect the compatible web runtime with affected writes still paused. Verify health/commit/schema, sign-in and tenant boundaries, private signed downloads, operator AAL2 access, billing reconciliation and public smoke. Resume authorized scheduled work only after its relevant checks pass. Paid tests retain their separate spending gate.

## Lost operator MFA factor (P20-49)

There is no password-only in-app bypass for operator access. A Supabase project administrator verifies the operator's identity through an established out-of-band channel before changing any factor. Verify the user ID and factor ID in the protected administrator console/API; retain any working factor. Use the current server-side `supabase.auth.admin.mfa.deleteFactor({ userId, id })` only for the specific lost factor. Never expose a service-role key in a browser or recover by adding an arbitrary email to `OPS_EMAILS`.

The administrator records the identity check, actor, time, user/factor IDs and reason in the restricted incident log and notifies the operator through an established channel. Enroll and verify a replacement factor, sign in again and prove AAL2 before opening `/app/ops`. Review existing sessions and revoke compromised sessions through the provider's documented controls. This manual administrative recovery is not falsely described as an in-app audit event. API reference: [Supabase administrative MFA deletion](https://github.com/supabase/supabase-js/blob/master/packages/core/auth-js/src/GoTrueAdminApi.ts).
