## Ordered database recovery

1. **Contain and select.** Stop new paid work through the operator maintenance switch, pause scheduled jobs and keep deployment pending. Record the last known-good app SHA, migration journal, recent encrypted backup and its recorded checksum. Preserve the affected database/service for investigation. Tell the founder which interval of writes may be missing; never infer zero data loss.
2. **Build an isolated target.** Use the fresh local Supabase stack or explicitly named throwaway project in [BACKUP_RESTORE.md](BACKUP_RESTORE.md). Match the production Postgres major and current Auth schema. No web instance, tick, backup writer, provider worker or email sender connects to it. Staging and production are prohibited drill targets.
3. **Authenticate/decrypt.** Use the separate read-only backup token and founder age key. Run `pnpm ops:restore-drill` with the documented target/identity/workdir/report options. It validates the recorded backup key, size and sha256, decrypts only into a private temporary directory, checks the manifest and refuses a nonempty target. Use a patched `pg_restore` version from BACKUP_RESTORE.md.
4. **Create schema from the reviewed repository.** `pnpm db:migrate` creates all tables, functions, grants and RLS policies. **Never restore schema from the dump.** The backup used `--no-privileges`, so importing its schema would omit security grants/revocations. Before loading data, `ops/cron/verify-restore.sql` captures the fresh migration's ACL, RLS and policy baseline.
5. **Restore data only.** The drill generates `pg_restore --data-only` output for public/drizzle and supported Auth data, loads it in one isolated transaction with `session_replication_role = replica`, and fails every restored live generation job in that transaction. Session/refresh/MFA-challenge/flow tokens are not restored. Do not let a restored job rerun providers or send mail. Preserve billing/email dedupe and ledger rows.
6. **Validate before any app connection.** Require every `verify-restore.sql` check: `tables_present`, `row_counts`, `latest_migration`, `ledger_total`, `ledger_balances`, `foreign_keys`, `acl_unchanged`, `ledger_functions_locked`, `live_jobs_reset`. The ACL and grant check must match the baseline from fresh migrations; anon/authenticated must not execute ledger/provisioning functions. Recheck RLS and workspace isolation. A row-count pass does not replace these security checks.
7. **Record and destroy the drill.** Save elapsed time and pass/fail against the seeded recovery target; report `restore_drill:last` through the authenticated report endpoint. Delete decrypted files and stop the local stack with its data removed. A throwaway cloud project is deleted manually immediately after the drill. Record the actual Auth-compatibility result rather than assuming local migrations match hosted Auth.
8. **Plan an actual cutover separately.** A successful disposable drill does not promote its target. Provision an isolated replacement with production controls, repeat the reviewed restore/ACL verification, reconcile post-backup Stripe activity and credit effects, configure Auth/DNS/storage and rotate compromised credentials. Get the founder's cutover decision with the known data-loss window and validated result before changing production endpoints. The drill command intentionally refuses production/staging targets.
9. **Reconnect in order.** After approved cutover, connect the web service with packs/purchases still paused. Verify health/commit/schema, sign-in and tenant boundaries, private signed downloads, operator AAL2 access, billing reconcile and public smoke. Then resume tick/backup/alerts. Confirm the first fresh encrypted backup and success records. Reopen purchases and packs only when the corresponding checks pass; paid smoke is a separately approved step.

## Lost operator MFA factor (P20-49)

There is no password-only in-app bypass for operator access. A Supabase project administrator verifies the operator's identity through an established out-of-band channel before changing any factor. Verify the user ID and factor ID in the protected administrator console/API; retain any working factor. Use the current server-side `supabase.auth.admin.mfa.deleteFactor({ userId, id })` only for the specific lost factor. Never expose a service-role key in a browser or recover by adding an arbitrary email to `OPS_EMAILS`.

The administrator records the identity check, actor, time, user/factor IDs and reason in the restricted incident log and notifies the operator through an established channel. Enroll and verify a replacement factor, sign in again and prove AAL2 before opening `/app/ops`. Review existing sessions and revoke compromised sessions through the provider's documented controls. This manual administrative recovery is not falsely described as an in-app audit event. API reference: [Supabase administrative MFA deletion](https://github.com/supabase/supabase-js/blob/master/packages/core/auth-js/src/GoTrueAdminApi.ts).
